# Complete Cloud Backup

Use after the scope router selects an explicit single project, or as the per-project subroutine inside a whole-device migration. An unqualified “上传云端”, “开始上传”, or “开始上传 skill” must first route through `all-projects-migration.md`; it must not silently select the current project. Once one project is selected, “原封不动” and “所有东西都不应该排除” require this complete filesystem backup, independent of Git's tracked-file list.

## Inventory Before Transfer

1. Resolve the project root and read applicable instructions. Do not expand to the user's entire computer, personal skill directory, or chat history unless requested. Files already inside the project, including existing backups, remain in scope.
2. Enumerate directory entries directly, including hidden files and empty directories, without using `.gitignore`, `git ls-files`, default archive exclusions, or extension/size allowlists. Check for protected browser-profile roots and reparse points before descent. Do not read or enumerate the contents of protected profiles when project instructions prohibit it.
3. Record every relative path exactly, plus entry type, size, timestamp, and totals. Filenames and directory names are payload identity: preserve Unicode, spaces, suffixes, case, and nesting without normalization or flattening. Include audio/video, toolchains, model files, caches, dependencies, generated outputs, `.git`, and ignored/uncommitted files. Report unreadable/locked entries and protected roots as unresolved, not absent. Preserve links as links only with a format and restore method that supports them; do not follow links outside the project or silently substitute their targets. If exact link preservation cannot be verified, report the limitation and leave exact completion pending.
4. Inspect large-file counts and total storage needs to choose a capable destination. Reuse existing private storage that fits. Read `setup-existing-project.md` if configuration is missing. Verify current provider file-size, capacity, upload, and cost constraints from official documentation; do not assume a Git repository can hold all project bytes.

Do not edit `.gitignore` or force-add all files to Git to implement this request. A non-Git project can be backed up without initializing Git.

## Sensitive Content Is An Explicit Decision

“Everything” is not a reason to publish credentials or to read browser authentication databases prohibited by project instructions. Identify protected roots by their directory names and stop before opening their contents.

Maintain an exceptions/pending list outside the payload, with paths or categories and reasons, without copying secret values. Do not silently filter them out and call the remaining archive complete. If the user's scope requires a protected item, explain the conflict and request the specific authorization needed before accessing it. Follow applicable permissions; do not rewrite project instructions to bypass a restriction. If authorization is not available, finish other permitted preparation and report that a complete backup is blocked.

Use supported local secret-review tooling within permitted paths. The bundled `secret-scan.ps1` is only a Git candidate check. A complete-backup review must account for ignored files, Git history/objects, nested archives, binary/configuration files, and its own scanning limits. Avoid treating any automated scan as proof of no secrets. If credentials or personal authentication state are explicitly authorized for backup, use a supported client-side encrypted archive/backup to user-controlled private storage, with the key supplied through a secure local prompt or credential store. Never embed a key in a command, log, project file, or cloud payload, and never request it in chat. If secure encryption/key handling is unavailable, report the blocker.

Encryption preserves file bytes on restore; it does not remove the need for authorization or a safe destination. Do not upload unreviewed archives or live browser profiles as an unencrypted shortcut.

## Preserve A Recoverable Snapshot

- Do not move, delete, overwrite, normalize text, transcode media, rescale images, or regenerate files in the source. Compression must be lossless. Keep empty directories, hidden entries, original paths, and timestamps where the format supports them. The bundled split-TAR workflow validates ordinary file bytes, directory inventory, paths, and restored timestamps, but does not prove preservation of NTFS ACLs, alternate streams, sparse allocation, hard-link relationships, or all other filesystem metadata. If exact filesystem fidelity is required, choose and verify a capable backup format; otherwise disclose the specific limitation.
- Create the archive and manifest outside the source tree, in an authorized staging directory with sufficient free space. This prevents the backup from recursively including itself. If permissions prevent suitable staging, request that permission rather than silently excluding source paths. Existing backups within the project remain included.
- Hash each permitted source file with SHA-256 and record it in a manifest. Record empty directories and link metadata separately. Detect files changing during hashing/archiving using before/after metadata, a final inventory comparison, and archived-content hashes. An active writer or `.git` mutation prevents a consistent snapshot; wait for a stable state or use an authorized snapshot-capable method. Never silently skip locked files or repeatedly retry a changing tree indefinitely.
- Use ZIP64 or another suitable lossless format, or a backup tool supporting exact restoration. Split archives or resumable uploads may be used for provider limits without omitting large files. Preserve all required parts and recovery instructions. Do not claim a transfer method is available before discovering the relevant tools.
- Keep credentials out of manifests and configuration. Manifests may contain private filenames: store them privately and encrypt them too when appropriate.

## Configure And Upload

Use the private destination supplied through `CROSS_DEVICE_SYNC_REPOSITORY` or the explicit command parameter. Confirm its exact identity, privacy, and accessibility before transfer. Do not silently substitute another repository. A private GitHub repository may store Git commits and Release assets, but selecting GitHub does not waive current file-size/storage limits or authorize reducing the backup scope. Recheck GitHub's official limits before each implementation. For recurring multi-gigabyte snapshots, prefer bounded private Release assets when they fit current limits; Git LFS charges and retention make it a poor default for whole-project snapshots. A Git-only route must preserve ignored and uncommitted files elsewhere before claiming full backup.

## GitHub private-backup workflow

When the user selects GitHub for a complete backup, do not add every live project file directly to the development repository. Create a point-in-time copy outside the source tree, converge it with repeated metadata-preserving copy passes, archive the permitted copy into bounded parts, calculate both per-file and per-part SHA-256 values, and verify the entire archive by reading it again. Protected browser-profile roots must be excluded before snapshot descent and repeated as archive exclusions; list them in the manifest without opening their contents. This preserves all other ignored files, uncommitted work, media, caches, empty directories, hidden entries, and the original `.git` without rewriting the source project.

Use `scripts/prepare-full-backup.ps1` with an explicit `-OutputRoot` on a drive selected after measuring free space. The helper performs its own conservative capacity and long-path checks and resolves Robocopy from the system directory reported by Windows rather than from `PATH` or the mutable `SystemRoot` environment variable. It rejects a drive root, user-profile root, Desktop, Documents, or Downloads by default; pass `-AllowBroadSourceRoot` only after the user explicitly names that exact broad root and confirms its whole contents. After convergence it compares the permitted source and snapshot inventories, timestamps, sizes, exact relative paths, and every file's SHA-256 before archiving, then repeats the live-source comparison after the archive has passed deep verification. Deep verification rejects non-zero data after the TAR end marker. It must not authenticate, upload, create a remote, or create a cloud repository. Only after an explicit upload instruction, use `scripts/upload-prepared-backup.ps1` with an existing private `owner/repository` destination. The upload helper rejects reparse paths and hard-linked prepared assets, pins the repository shorthand to `github.com`, validates and adopts GitHub's canonical repository identity, regenerates README and restore instructions through exclusive checked file handles using deterministic UTF-8 without a BOM and LF line endings, creates canonical `RELEASE_BINDING.json` with the repository, tag, and manifest SHA-256, and verifies packaged restore helpers against the installed Skill. It records every expected asset hash before its final deep verification, then uses an exact GraphQL lookup so only a confirmed absent tag permits draft creation. Before every missing-asset upload it refreshes the Release state and manifest identity; it never uses `--clobber`, and an existing mismatched asset requires a new tag rather than remote replacement. It compares every remote asset's exact size and `sha256:` digest, rechecks repository privacy immediately before and after publication, and publishes only after all expected assets match and no unexpected asset is present. If the post-publication privacy check fails, it attempts to return the Release to draft, queries the Release again, and reports potential exposure unless the new query confirms the draft state.

Completion requires a successful final Release query, a Boolean published status, the requested tag, a valid HTTPS URL, and matching assets. Missing or malformed status, failed queries, or a Release that changes back to draft must not be reported as successful. A failed confirmation can occur after publishing; inspect the remote state before retrying or claiming completion. When an identical published Release is found, distinguish verified remote state from work performed now: report zero assets uploaded this run and do not claim that this run published it.

When the user says to prepare now and upload later, stop after the preparation script succeeds. Do not log in, create a GitHub repository, add a remote, or transfer any object. A later unqualified upload instruction must rediscover all registered local projects and create fresh per-project snapshots; only an explicitly narrowed single-project instruction may refresh just the named project. Never assume an older prepared archive is current.

If the source is actively changing, do not keep re-archiving the live tree. First use convergence passes to create an external snapshot, require two consecutive no-change passes, then archive that static copy. If convergence cannot be reached, report the live writer as the blocker and keep the partial snapshot for retry.

Use a new dated snapshot or versioned object prefix. Do not delete or replace previous cloud content by default. Each transfer requires a current explicit instruction covering the reviewed destination and inventory. Ask again for a changed account, destination or visibility, materially changed scope, detected credentials, new cost, destructive replacement, or an actual permission gate. A Skill-edit request never starts an upload.

Upload all parts, the private manifest, and restoration information. Every new v2 manifest must contain the configured `source_device` and actual Windows `source_computer`; verify both before upload. If interrupted, inspect the draft Release and resume only missing assets. If an existing asset has a different size or digest, do not replace it; use a new Release tag. Keep the repository private. Publishing a remote-asset-verified Release inside that already-authorized private backup repository completes the upload step; it does not establish restore verification. Never change repository visibility or create a public share link.

## Verify Completion And Restore

Distinguish these states in user-facing reports:

- **Prepared locally:** inventory/archive exists; no upload has been proved.
- **Uploaded, verification pending:** remote upload was acknowledged, but completeness/integrity has not yet been verified.
- **Complete backup verified:** every in-scope entry is accounted for, no unresolved exception remains, remote payload bytes match the local snapshot, and restore verification has passed.

Compare remote object counts/sizes and a documented content checksum where available. Do not assume an ETag is SHA-256 or MD5. If the provider exposes no reliable checksum, download the uploaded archive/parts and compare their hashes. A successful CLI exit code, a Git push, or matching filenames alone is insufficient.

Restore with the locally installed `scripts/restore-full-backup.ps1`, passing the downloaded asset directory through `-BackupPath`, the independently confirmed `owner/repository` through `-ExpectedRepository`, the independently confirmed manifest SHA-256 through `-ExpectedManifestSha256`, and the known tag through mandatory `-ReleaseTag`. New backups must include `RELEASE_BINDING.json`; the helper verifies all three external identity values against the embedded repository, tag, and manifest before restoration. For a legacy backup without this file, require both `-AllowLegacyUnboundRelease` and an independently confirmed `-ExpectedManifestSha256`, and report explicitly that the old Release tag is externally supplied rather than cryptographically bound. Generated `RESTORE.txt` instructions must include the actual repository, tag, and manifest SHA-256 and must not direct the user to execute the downloaded helper copy. This keeps executable verification logic in the trusted installed Skill instead of running a remote copy. Before creating output, calculate the longest destination path from the manifest; paths of 260 characters or more require Windows `LongPathsEnabled=1`, and paths at the extended-path limit require a shorter destination. Restore into a new directory, reject archive paths escaping that directory, and precreate every manifest directory and regular file as an ordinary path. Hold delete-denying handles on the destination and every expected output path while combining and extracting; after extraction, also hold read-only-sharing handles on every restored regular file through full verification and success reporting. Compare every restored file's SHA-256 and the exact file/directory path inventory against the manifest. A missing, added, renamed, normalized, case-colliding, or relocated path fails verification. The combined TAR must remain open with write/delete sharing denied from creation until `tar.exe` finishes, so the verified file cannot be replaced between combination and extraction. Do not overwrite the working project to test restoration. If a full restore cannot be checked, report that verification as pending rather than claiming exact restoration. If the user explicitly accepts a narrower scope, record it and describe the result as that narrower backup, not the original unqualified “everything”.

The final report gives the established device label, operation date/time and timezone, private destination, Release tag, manifest SHA-256, snapshot creation time, file count and byte total, verification performed, unresolved exceptions, and how to restore. Keep operation date and snapshot date separate. Do not claim that an identical file copy guarantees another machine can run hardcoded paths or machine-specific dependencies without setup.
